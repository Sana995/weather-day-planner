# Personal Weather Assistant

Personal Weather Assistant is a small full-stack app that turns a live weather
forecast into personalized, streamed advice. Enter a city, a date, and a short
profile (activity, cold tolerance, heat tolerance), and the assistant streams
back a markdown recommendation — what to wear, what to do, and practical tips —
generated by an LLM that is grounded in the real forecast for that place and
time. Once the answer lands, **Sunny** — the app's chat assistant — picks up
the conversation for follow-ups.

## Features

- **Day recommendation** — enter a city + date and a personal profile; get a
  streamed, LLM-written recommendation with `### Outfit`, `### Activities`,
  and `### Tips` sections, grounded in the real forecast for that day. The
  prompt is also grounded in the city-local calendar and clock: the server
  tells the model whether the date is today/tomorrow/a weekday and, for
  today, which hours are already past — and invites date-aware knowledge
  like the Perseids on a clear mid-August night. `### Activities` opens with
  the adapted plan in prose, then lists concrete ideas and attractions as
  bullets — including festivals and recurring events the model is confident
  about — and on sunny days the Tips must carry SPF sun protection. Untick
  "Include activity ideas" (`includeActivities: false`) to get just
  `### Outfit` + `### Tips` — unless "Include local attractions" stays
  ticked, in which case the answer carries a standalone `### Attractions`
  section instead: a weather-fit list of real places, deliberately not a
  day plan.
- **Hiking thinks regionally** — "hiking" and "outdoors" are separate
  activities. A hiking answer reaches for the real hiking country near the
  city (Pohorje above Maribor; the Julian Alps around Kranjska Gora near
  Bled), never just the city's own parks.
- **Local festivals, keylessly** — whenever activity ideas are on, the
  server extracts festival/event mentions from the city's Wikivoyage page
  (the same keyless source as the guide notes) and hands them to the model
  undated. Festival dates shift year to year, so the model season-filters
  them and phrases a plausible one as worth checking ("Festival Lent may
  well be on around now — check the programme") instead of asserting dates
  from memory. Sunny's `get_attractions` tool returns the same events
  field mid-chat.
- **Real dated listings via SearchApi (optional)**: set `SEARCHAPI_API_KEY`
  and the server pulls live event data for the city from
  [SearchApi](https://www.searchapi.io/). It tries the structured Google
  Events engine first and falls back to a plain Google search for
  "<city> events <month year>", whose organic snippets (venue calendars,
  ticket sites) carry real dates. Either way the model may only state
  dates a listing itself carries: matching events get their own
  Activities bullet with time and place, the rest are skipped. Degrades to
  nothing without the key. Details in
  [SearchApi integration](#searchapi-integration).
- **Date range: today → +5 days.** This is a hard limit, not an oversight —
  it matches exactly what OpenWeatherMap's free "5 day / 3 hour forecast"
  plan exposes. There is no free daily forecast beyond that horizon, so
  requests for dates outside the window fail fast with a clear 404 instead
  of silently returning wrong data.
- **Structured profile inputs** — activity, cold tolerance, and heat
  tolerance are dropdowns backed by one shared enum (`shared/src/profile.js`), so the
  client UI and the server's request validation can never disagree on what
  counts as a valid value.

It also has:

- **Token-by-token SSE streaming** — both `POST /api/recommend` and
  `POST /api/chat` stream the LLM completion as Server-Sent Events (one
  small text fragment per `event: token`), so the UI renders the answer
  incrementally instead of blocking on the full response.
- **Local attractions** — check "Include local attractions" on the form and
  the request sends `traveling: true`; the flag is independent of activity
  ideas: with activities on, attractions ride inside `### Activities` as
  add-ons to the plan; with activities off, they get their own
  `### Attractions` section. Only with the flag set does the server fetch real
  nearby points of interest from Geoapify Places (indoor picks — museums,
  culture — on wet days, outdoor sights/parks otherwise; nature and trails
  for hiking) if `GEOAPIFY_API_KEY` is set, plus Wikivoyage's "See"/"Do"
  guide notes for the city (keyless, no signup needed). Both are handed to
  the LLM with an explicit instruction to blend them with its own knowledge
  and never invent place names. Either source degrades independently to
  empty on any failure or missing key, with no error and no user-visible
  break — just a slightly more generic recommendation.
- **Sunny, the follow-up chat** — once a recommendation finishes streaming,
  a chat panel titled "Chat with Sunny" appears underneath it. Sunny is an
  assistant with a personality — warm, human, and not a weather bulletin:
  it answers what you actually asked and only brings the forecast in when
  it changes the answer. It posts to `POST /api/chat` (SSE), where the
  server runs a Groq tool-calling loop with two tools, `get_weather` and
  `get_attractions`, so Sunny fetches a real forecast (and real
  attractions) for any place mentioned mid-conversation instead of
  guessing — up to 3 tool-call rounds, then one final round with tools
  disabled so a tool-happy model can never loop forever. The event stream
  adds `event: tool` frames (`{name, label}`) alongside `event: token`,
  which the UI shows as a status line ("Sunny is checking the forecast for
  Ljubljana…") while a tool runs. Conversation state lives entirely on the
  client — capped at 20 turns and 2,000 characters per message — and is
  re-sent in full every turn, with the original recommendation riding
  along as the first assistant message so the chat has context from turn
  one.
- **Per-city forecast cache** — `getForecast()` caches each city's
  OpenWeatherMap response in memory for 10 minutes, so repeated requests
  for the same city (e.g. switching profile fields and re-running) don't
  re-hit the upstream API every time.

## Architecture

```
                +-----------------------+
                | Browser (client)      |
                | React 19 + Vite       |
                | http://localhost:5173 |
                +-----------------------+
                            |
                            | fetch('/api/...')
                            v
                +-------------------------+
                | Vite dev server (:5173) |
                | proxy: /api/* -> :3001  |
                | (client/vite.config.js) |
                +-------------------------+
                             |
                             | HTTP (dev-time proxy)
                             v
                +----------------------------+
                | Express API server (:3001) |
                | (server/src/routes.js)     |
                |                            |
                | GET  /api/health           |
                | GET  /api/weather          |
                | POST /api/recommend  (SSE) |
                | POST /api/chat       (SSE) |
                +----------------------------+
                               |
         +---------------------+---------------------+
         |                     |                     |
         v                     v                     v
+-----------------+   +-----------------+   +-----------------+
| OpenWeatherMap  |   | Geoapify + Wiki |   | Groq            |
| 5-day/3-hour    |   | + SearchApi     |   | LLM chat        |
| forecast        |   | (POIs + events) |   | (streamed)      |
+-----------------+   +-----------------+   +-----------------+
```

The upstream API keys (`OPENWEATHER_API_KEY`, `GROQ_API_KEY`,
`GEOAPIFY_API_KEY`, `SEARCHAPI_API_KEY`) live only in the server-side `.env`
file, read once at startup by `server/src/index.js`. The browser never sees them — every
upstream call is made from the Express server, and the client only ever
talks to `/api/*` on the same origin (proxied to `:3001` in dev).
Wikivoyage needs no key at all. Geoapify is only called when a request sets
`traveling: true` — the "Include local attractions" checkbox on the form.
Wikivoyage is also consulted (keylessly) for the events extraction whenever
activity ideas are on, and SearchApi, when its key is set, for live dated
listings at the same moments.

Workspace layout:

```
.
├── client/   React + Vite UI (day form, weather card, streaming panel, Sunny chat)
├── server/   Express API: routes, validation, forecast fetch+cache, Groq streaming, POI + SearchApi events lookup
└── shared/   Profile enums (@weather/shared) imported by both client and server
```

## SearchApi integration

Live, dated event listings come from [SearchApi](https://www.searchapi.io/),
in [`server/src/events.js`](server/src/events.js). It is optional: without
`SEARCHAPI_API_KEY` the lookup is skipped and the rest of the app works the
same.

One lookup, per city and month:

1. **Google Events first.** `GET https://www.searchapi.io/api/v1/search`
   with `engine=google_events`, `q=Events in <city>`, `gl=<country code>`
   (from the forecast's city) and `hl=en`, the only language this engine
   accepts. Up to 8 items from the `events` array become
   `{title, when, venue}`:
   - `when` is `start_time` (`"Aug 26, 7:00 PM"`, absolute), falling back
     to `date`, which can be relative (`"Tomorrow"`).
   - `venue` is `venue`, falling back to `address` (a city or
     neighbourhood).
   - The mapping follows SearchApi's 2026-08 response format, where `date`
     and `venue` are plain strings. A field of any other type maps to `""`.
2. **Plain Google search as a fallback.** When Google shows no events
   panel for the city, one more call with `engine=google` and
   `q=<city> events <Month YYYY>`. Up to 6 `organic_results` with a snippet
   become `{title, snippet}`; venue calendars and ticket sites put real
   dates in those snippets.
3. **Into the prompt.** The listings reach the model in their own block,
   and the system prompt allows only dates a listing itself states. Sunny's
   `get_attractions` chat tool returns the same listings as `liveEvents`.

Behaviour around it:

- **Auth:** the key is sent as `Authorization: Bearer <key>`, never in the
  query string, so it cannot leak through URLs or logs.
- **Cache:** results are kept for 10 minutes per city and month, and
  concurrent requests share one upstream call.
- **Failures:** a non-200 answer (bad key, used-up quota) or a 5-second
  timeout is logged and treated as "no listings". After a failure the
  fallback search is skipped, since the same key would fail again and
  waste a billable request. Failures are never cached, so the next request
  retries.
- **Cost:** a lookup costs one request, or two when the fallback runs.

## Prerequisites

- **Node.js ≥ 20** (uses native `fetch`; developed and tested on Node 22).
- Free API keys:
  - **OpenWeatherMap** — <https://home.openweathermap.org/api_keys> (the
    free "Current Weather and Forecasts" plan, no credit card required).
    **Fresh keys can take up to ~2 hours to activate** — if the server logs
    `OpenWeatherMap rejected the API key`, this is almost always why; just
    wait and retry, no code or config change needed.
  - **Groq** — <https://console.groq.com/keys> (free tier). Defaults to the
    `llama-3.3-70b-versatile` model unless `GROQ_MODEL` is overridden.
  - **Geoapify** (optional) — <https://myprojects.geoapify.com/>. Powers
    the real-attractions list in traveling mode; the app works fully
    without it — leave `GEOAPIFY_API_KEY` empty and traveling mode falls
    back to Wikivoyage guide notes (keyless) plus the LLM's own knowledge.
  - **SearchApi** (optional): sign up at
    <https://www.searchapi.io/users/sign_up> (no credit card), then copy
    the API key from your SearchApi dashboard. Powers live, dated Google
    Events listings in the Activities section; sign-up comes with 100 free
    requests. Leave `SEARCHAPI_API_KEY` empty and the app still surfaces
    guide-derived (undated) festival mentions keylessly.

## Setup

```bash
git clone <repo-url>
cd weather-day-planner
npm install                # installs root + server + client + shared workspaces
cp .env.example .env       # then fill in your keys
```

`.env.example` (repo root) lists the variables to fill in:
`OPENWEATHER_API_KEY` and `GROQ_API_KEY` (required), `GROQ_MODEL` (optional,
defaults to `llama-3.3-70b-versatile`), `GEOAPIFY_API_KEY` (optional POI
grounding) and `SEARCHAPI_API_KEY` (optional live event listings; both
degrade silently to nothing when empty), plus `PORT` (defaults to `3001`).

`.env` is git-ignored — never commit real keys.

## Running

```bash
npm run dev
```

This runs the server and client concurrently:

- API: `http://localhost:3001`
- Client: `http://localhost:5173` (open this in your browser; it proxies
  every `/api/*` request to the server)

## Testing

```bash
npm test
```

Runs both workspace suites (server: Vitest + Supertest; client: Vitest +
Testing Library/jsdom) via `npm run test --workspaces --if-present` (the
`--if-present` flag skips the `shared` workspace, which has no test script
of its own):

- **Server** — 163 tests across `places`, `events`, `prompts`, `chatTools`, `groq`,
  `validate`, `weather`, and `routes` test files.
- **Client** — 36 tests across `api`, `WeatherCard`, `Recommendation`,
  `WeatherForm`, `ChatPanel`, `ProfileChips`, and `App` test files.
- **199 tests total.**

The suite is **fully offline and needs no API keys**: every upstream call
(`fetch` to OpenWeatherMap/Geoapify/Wikivoyage, the `groq-sdk` client) is
mocked or stubbed at the module boundary, so `npm test` works identically
with an empty `.env` or no `.env` at all.

## Example usage

**Day recommendation.** Open `http://localhost:5173`, set City to `Zagreb`,
change Date to tomorrow (it defaults to today), and set
Activity/Cold tolerance/Heat tolerance to `tourism` / `average` / `average`
to match the run captured above. Click **Get recommendations**. A weather
summary card appears first (`Donji grad, HR — 2026-08-07`, `23–35 °C`,
`scattered clouds`, `rain 26%`, `wind up to 3.67 m/s`, plus an hourly
strip), and directly below it the recommendation panel starts filling in
token by token, ending with the `### Outfit / ### Activities / ### Tips`
markdown shown in the API examples above. When it finishes, the
**Chat with Sunny** panel appears underneath for follow-ups.

**Error paths in the UI:** an unknown city surfaces the server's `"City
not found"` message as an error card at the top of the answer column — the
panel on the right where results appear, not inline text under the form;
picking a date outside the allowed range is prevented client-side (the
date input's `min` and `max` are clamped to today…+5 days), and is also
rejected server-side with the 404 shown above if bypassed (e.g. via a
direct API call).
